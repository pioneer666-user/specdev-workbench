# 已有业务修改指引

本指引管"已有业务或其产物的再次修改"——业务完整交付过当然算，还在半路的也算：图没画、
证据没补、快照没存过，都不挡进入；本次改什么，就按需读取相关材料。缺的产物（图、详情、
证据、快照等）只在影响本次修改的正确性或产品操作时才补齐，不要求先凑齐整套资产。首次实现
见 [implementation.md](implementation.md)，首次证据补录与差异核对见
[evidence-review.md](evidence-review.md)；本指引不重复它们的规则，只管"再次修改"多出来的事。

一句话定义（公共版）：

> 修改已有业务时，识别本次影响范围，更新受影响的实现和说明，验证新行为与相关旧行为，
> 并保留可追溯的历史。

**规则分层**（本指引只写第一类，其余引用或让位，不搬运）：

| 类型 | 例子 | 放在哪里 |
|---|---|---|
| 通用可靠性要求 | 不覆盖已有工作、不遗漏相关改动、验证修改结果、如实报告差异 | 本指引主流程 |
| Archify 产品约束 | 节点 ID 与详情对应、证据按固定提交读取、快照保存范围 | 引用现有产品约定（project-contract.md 等） |
| 项目的工作习惯 | 每个小功能单独批准、修复轮数上限、页面由谁验收 | 目标项目自身规则；冲突时按目标项目执行 |

## 1. 确认当前状态与本次目标

- 阅读与本次修改**相关**的规格、代码、图、详情和证据；有疑问再追查历史，不默认通读
  整个业务。
- 分清四样东西：**文档现在怎么规定、代码实际上怎么做、本次要求改成什么、哪些还不清楚**。
  旧文档可能过时，不能直接当成实现事实——代码与文档的一致性用
  [evidence-review.md](evidence-review.md) §4 的核对思路确认，不凭文档自述。
- 动手前检查已有未提交改动，避免覆盖或混入别人的工作；发现来源不明的改动怎么处置，
  按目标项目规则。
- 用户已明确授权的修改直接推进；只有信息不足、要求冲突或范围扩大时才补充确认。

## 2. 判断影响范围与验收方式

- 说明哪些规则（FR/AC）、代码、节点、详情和证据可能受影响，以及用什么证明修改完成
  ——这就是本次修改的影响面与验收口径，动手前先摆出来。
- 简单修改几句话说清即可，不强制新增计划、任务单或审批表（与
  [implementation.md](implementation.md) §1 同一口径）；改动跨模块或影响面广时按目标
  项目规则落文件。
- 目标是一个**完整、可验证的变更**：一次业务修改同步几个相关文件很正常，不按文件
  数量机械拆分，也不把无关文件捎带进来。

## 3. 确认修改前的状态可以追溯

- 复用已有 Git 提交或管理页快照即可；确有尚未保存、需要保留的状态时，再提示处理。
- 不要求每次修改前新建快照或空提交。两样东西用途不同：**Git 留存代码状态，管理页
  快照登记图的版本**（三个图文件＋阶段，见 [project-contract.md](project-contract.md) §4）。

## 4. 按影响范围修改和同步

不要求每次改齐"规格、代码、测试、图、详情、证据"六样，按修改情况取用：

| 修改情况 | 通常需要处理 |
|---|---|
| 文字纠错，业务含义未变 | 修正文案；检查引用是否受影响 |
| 代码重构，外部行为未变 | 验证原有行为不变；检查相关证据是否仍准确 |
| 业务规则或流程变化 | 更新规格、实现和必要测试；同步受影响图与详情 |
| 补齐已有实现的出处 | 查证并更新证据（evidence-review.md §2），不顺带重画业务图 |

- **ID 稳定的边界**：语义未变的业务、图、节点、规则 ID 保持稳定
  （[workflow.md](workflow.md) §3.2、[specification.md](specification.md) §5——规则编号
  作废不回收，新增续编新号）；真正删除、替换或拆分的节点，同步处理关联引用（详情
  分节、证据指向、连线），**不为保留编号而让旧 ID 偷换含义**。
- **证据沿用 4b 规则**：按引用提交查证内容和行号，无法核实的明确标记。旧证据按固定
  提交读取，**不因后续代码变化自动失效**——要检查的是这条证据还能不能支撑当前描述：
  相关实现变了才按 evidence-review.md §3 顺序更新引用（先提交实现、再提交证据），
  无关改动不必把证据刷成最新提交。

## 5. 验证本次修改与相关旧行为

- 不只验证新要求满足，也验证**受影响的原有行为**仍然成立；验证范围由依赖关系决定，
  不简单等同于"改了哪几行"。
- 图源未变且已有校验回执仍适用时复用，不重跑；图源变化时按
  [workflow.md](workflow.md) §4 重新校验（五判据全过才算）。
- 规格、图、详情、源码之间仍有差异就如实报告（差异报告用
  [evidence-review.md](evidence-review.md) §5 的六列格式），不能靠删条件或改描述让
  结果看起来一致。

## 6. 交付变化与未完成项

报告四件事：

1. **改了什么及原因**——原因写在交付报告或提交说明里，不强制另建变更日志；
2. **影响哪里**——受影响的规则、代码、图、详情、证据清单；
3. **如何验证及结果**——未验证项如实标注；
4. **还有什么未决或未验证**。

提交与发布遵循目标项目的授权规则；需要在管理页登记新版本时，保存仍由用户亲手完成
（[project-contract.md](project-contract.md) §4）。

## 7. Archify 特有事实（引用，不重复发明流程）

- 保存操作由用户在管理页完成，本指引只提醒不代存（project-contract.md §4）。
- 历史快照保留当时的图、详情和证据；业务文档及部分名称信息不随快照回退——看历史
  快照要核对当时的业务文档时，按快照指向的提交另行用 Git 核对。
- 保存可能返回已有快照（三个图文件与阶段和已有快照相同时），不能承诺"每次修改都会
  产生新快照"；以实际返回的快照为准。
- 未经核实的内容不因进入修改流程就被标成已实现——四类标注口径不变
  （project-contract.md §2.5、evidence-review.md §4）。

## 8. 边界

- 本指引管已有业务或其产物的再次修改；从零开始的新业务从 SKILL.md 设计段主流程进入，不走本文。
- 拿不准归属的差异（该改代码还是该改规格）不自行选择，带候选交用户裁决
  （与 evidence-review.md §6 同一条纪律）。
- 本指引自身添加新规则前先问三件事：**它解决了什么实际问题、现有规则为何没解决、
  最轻的补救是什么**——单个项目的偏好留在项目规则里，重复出现、能解释清楚的共性问题
  才进本指引。

# 业务规格编写指引

本指引与 `assets/spec-template.md` 配套：模板管"长什么样"，本指引管"怎么写、怎么问、怎么自查"。

写完的文档要能让一位看过它的业务裁决者回答三个问题：**要求是什么、什么算做到、哪些还没定**。

## 1. 何时写、何时改

- **开发新功能**：整理需求后、动手实现或出图之前写，作为后续工作的依据。
- **修改已有业务逻辑**：在原有文档上修订，不另建新文档。沿用原规则编号，新增规则续编新号；
  删除的规则编号作废不回收，**不为整齐重新编号**。
- **日常开发**（不改业务逻辑）：不需要这份文档，不要为了"有文档"而写。
- 讨论阶段的草稿不算已裁决内容；未获批准的规则不得写成定案。

## 2. 从口头需求到文档

### 2.1 提取

从需求描述里找出四样东西：**角色**（谁在用）、**动作**（做什么）、**数据**（动什么）、
**约束**（不能怎样）。找不出来的部分就是缺口，进入歧义扫描。

### 2.2 歧义扫描

逐类过一遍，每类标"清楚 / 部分 / 缺失"；标"部分/缺失"的生成候选问题：

| 类别 | 看什么 |
|---|---|
| 功能范围 | 核心目标；明确不做什么；角色之间的区别 |
| 数据 | 关键对象；唯一性怎么判定；状态怎么流转 |
| 交互 | 主要路径；出错、为空、等待时用户看到什么 |
| 质量属性 | 性能、并发、安全与合规——有法律或资金影响时必须问清 |
| 边界 | 失败、重复、中断、越权、数据损坏时的行为 |
| 术语 | 同一个词是否处处同义 |

### 2.3 提问与记录（三条硬规则）

1. **集中提问，给足候选**：问题一次集中列出，每个问题附候选答案和推荐项，等裁决人选择；
   不一次一个地挤牙膏，也不把问题吞掉自己猜。
2. **不设提问数量上限**：真实业务缺口有多少就问多少——省掉的问题不会消失，
   只会在实现时变成擅自决定。
3. **回答三态，如实记录**（仅限影响业务的决策问题，日常开发问答不进文档）：
   - **作者已拍板**：原话逐字记入「澄清记录」，标注时间戳；构成规则的同步更新「规则」节并在记录中关联编号，其他决定更新相应正文；
   - **AI 建议**：标明"尚未经作者认可"，可以写进分析，不得写成规则定案；
   - **待裁决**：正文相应处标 `【待裁决：<具体问题>】`，保持可见，不隐藏也不假装解决。

编写者按行业惯例补的默认值，一律进「假设与默认」节——**禁止把合理猜测写成作者批准**。

## 3. 各章节怎么写

| 章节 | 写什么 | 不写什么 |
|---|---|---|
| 目标 | 为谁解决什么问题，一到三句 | 做法、技术、实现细节 |
| 业务原则 | 几条底线立场，用于裁决规则争议 | 具体规则（去「规则」节） |
| 规则 | 带编号的断言，每条能判对错 | 流程叙述、场景描写 |
| 边界与失败情况 | "什么情况 → 应有什么结果"，引用规则编号 | 另立无编号的新规则 |
| 验收 | 场景式或度量式判据（写具体条件与预期结果），注明覆盖哪条规则 | 实现步骤；对规则条文的整段照抄 |
| 场景与用法（按需） | 谁在什么情况下做什么、为什么重要 | 规则定义 |
| 领域词汇（按需） | 定义＋不是什么 | 与全局词汇表重复的定义 |
| 假设与默认（按需） | 编写者补的默认值及来源 | 已拍板的规则 |
| 澄清记录（按需） | 三态问答，原话带时间戳 | 日常开发问答 |

## 4. 写作红线（四条，违反即返工）

1. **断言形式**：每条规则必须能写成一个能判 True/False 的检查；无法判断对错时，
   指出缺失的条件或判据，标为【待裁决】；未经作者同意，不降低要求强度。
2. **判卷，不是抄答案**：文档让人能判断实现的对错，不是让人逐行翻译成代码。
3. **篇幅优先给边界**：失败和异常详写；顺利路径的文档价值趋近于零。
4. **单一真理来源**：规则在「规则」节统一定义；验收写具体条件与预期结果，
   图和详情写理解所需的业务解释，并引用规则编号，不新增或改变规则。

## 5. 编号约定

- 新业务：规则从 **FR-001**、验收从 **AC-001** 起编；编号一经使用即稳定，修订内容不改号。
- 已有业务：沿用原编号体系；新增规则接续最大号续编。
- 图、详情、证据引用规则时引用编号，不复制规则全文。

## 6. 交付前自查

自查结果列入交付报告（说明每项过/不过及原因），不另建独立清单文件：

- [ ] 必备章节齐全：目标 / 业务原则 / 规则 / 边界与失败情况 / 验收。
- [ ] 每条规则可测试：能判对错；无技术栈、接口、框架等实现细节。
- [ ] 每条验收可核对：给定—当—那么，或可度量指标；注明覆盖的规则编号。
- [ ] 失败情况有归属：边界条目要么引用了规则编号，要么已标【待裁决】。
- [ ] 无未替换的占位符；不适用的按需章节已整节删除。
- [ ] 三态如实：作者原话带时间戳；AI 建议与待裁决没有被写成已批准。
- [ ] 术语一致；规则定义只在「规则」节出现，其他章节引用编号且未新增或改变规则。
- [ ] 已追认的假设已离开「假设与默认」：构成规则的进了「规则」节，澄清记录留有原话、时间与关联编号。

## 7. 边界

- 本指引只管业务规格的编写与修订；出图、证据、管理页登记另有约定，不在本文件展开。
- 模板是本 Skill 内的工作模板；是否并入项目的正式文档体系，由项目所有者在使用后裁决。
